# Provider migration: Sign in with ChatGPT

**Decision (2026-11-27): approved direction, not implemented.** Replace the product's Claude/Anthropic runtime with OpenAI's supported Sign in with ChatGPT plan-usage flow while preserving the existing Ableton extension, tool semantics and Outcome D architecture. This is a scope and roadmap decision; implementation requires an execution-ready Phase 15 plan. It does not change the Claude Code development harness into a product dependency or require migration of its historical evidence.

## Official contract / feasibility gate

Sources checked 2026-11-27:
- [Sign in with ChatGPT quickstart](https://developers.openai.com/siwc/quickstart), [plan usage overview](https://developers.openai.com/siwc/token-sharing-open-source), [registration/sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).
- Eligible Plus/Pro accounts and eligible open-source/locally hosted clients, including selected private clients, can authorize plan usage. GitHub repo is public, but that alone does not prove eligibility; no license file was identified in this checkout. Do not claim eligibility or add a license/publish further source without the owner's decision. Verify supported registration and a completed minimal request on the intended account/model before investing in the full migration. If unavailable, stop and report; eligible [Pro API credits](https://help.openai.com/en/articles/20001626-api-credits-benefit-for-eligible-chatgpt-subscriptions) are a separate option, not an automatic fallback. No unofficial ChatGPT backend endpoints, borrowed Codex tokens, scraping, cookies, permission bypass, automatic API-key switch or Anthropic spend.
- Use system-browser OAuth/OIDC with PKCE, state/nonce checks, a persistent host identifier, issued per-account registration, validation of the returned ID token and granted plan-use scopes (not merely identity). Use the documented loopback callback; securely persist tokens and refresh metadata in host-only storage or a permission-compatible local companion. Never expose access/refresh tokens, authorization codes, ID tokens, endpoint credentials, or secret-bearing URLs to webview messages, logs, analytics, Git or issue reports. User completes consent personally. Handle denial, expired/revoked token, account switch and usage limits clearly; sign-out clears the selected connection as documented. Do not silently mix histories across accounts.
- Prefer direct official Responses API (OAuth bearer authorization) from the Node host using the beta's supported native Fetch stack. The original SDK UI has a modal primitive but no documented system-browser opener in the pinned API; prove OS browser launch/loopback callback, secure storage, refresh, AbortSignal and streaming in **installed** Live, not just standalone Node or developer host. If host cannot support these operations under intended permissions, evaluate a minimal user-launched local companion for auth/inference only with bounded authenticated loopback IPC; no generic command execution, external listener, or direct SDK/tool access. Keep the same in-Live chat and local tool runner; propose that architectural change to the owner before implementation.
- Preview requests require store:false, stream:true, complete explicit input history, and developer instructions rather than a system-role message. Use the account-specific model list (no assumed entitlement to a specific GPT model). No previous_response_id over HTTP or hosted tools; only local custom/function tools grouped into namespaces or supplied as additional tools, according to the current contract. No max_output_tokens, max_tool_calls, prompt_cache_retention or explicit Anthropic cache controls on this route. Confirm exact schema/stream support in the spike; use response.completed as success, distinguish response.failed, incomplete and interrupted streams. No mutations from partial streamed arguments or unconfirmed requests.

## Proposed Phase 15 completion sequence (planning-level)

Detailed execution contract for Phase 15.3 is [approved](active/phase-15.3-plan.md); roles are recorded in PROJECT.md. A later dedicated Astra/low plan is required for each subsequent stage before implementation. Each substage has a stop gate. First review checkpoint: reconcile and deliver the existing Phases 10–15.2 local baseline with these docs to main via PR; the owner reviews it before the feasibility spike. No new migration code in that PR. The owner reviews each subsequent phase PR before the next work begins.

1. **15.3 Eligibility + installed-host spike (backend/test).** Verify official account/registration route with user consent, supported browser opening and callback/secure storage; complete one minimal streaming request and a harmless synthetic custom function call/output. Record beta/host versions, scopes names only, sanitized status and usage, response terminal state and whether native fetch/abort works. Check package contains webview asset. If ineligible or host blocks, pause for owner route choice; do not implement a workaround.
2. **15.4 Provider adapter + contract (backend).** Introduce neutral provider boundary; convert Responses streaming text and fully assembled function calls to the existing runner; map each call/result ID exactly once, preserve batch order, fail closed on malformed/unknown/duplicate or incomplete calls. Retain tool schema meaning, validate arguments locally even if provider strict mode differs. Preserve execution order and confirmation gate; check non-vacuous approve/decline/cancel, rollback, no stale refs. Use response.completed terminal success, structured failures, bounded retries without replaying a mutation. Model identifiers from account catalog.
3. **15.5 Credentials, UI, settings + transcript (backend/frontend; protocol contract before parallel split).** Use approved auth flow; option to cancel out of sign-in; no token sent to UI. Login/consent denial, refresh/revocation, sign-out, switch accounts, clean first run and reconnect. Keep old Claude config/transcripts as historical local data, never read as input to ChatGPT or overwrite without explicit choice. Host-only per-account persistence and neutral history version; no implicit provider fallback.
4. **15.6 Context and usage (backend/test).** Rework estimator/eviction for explicit Responses history: preserve call-output pairing and terminal/reasoning context as required, compact stale tool output only, drop whole old turns if necessary, keep current and recent context, validate snapshot size. Log sanitized usage counts, including total input and cached details if returned; do not add cached tokens again where already included in input. No unsupported cache controls or claims of guaranteed reuse; verify actual provider caching if observed, classify unavailable/unsupported honestly. Mock budget-crossing cases and API usage-limit recovery.
5. **15.7 Regression/build and current beta installed smoke (test/reviewer).** Run local lint, type check, full Vitest, build and configured harness validation; update opt-in schema validation (preserve historical Anthropic probe until retired; never run without authorization). Compare pre-migration 951 behavioral proofs, no regressions or weakened tests. On a disposable Set with explicit live/operator approval: first-run sign-in and reconnect, read project/scope, rename/undo, create/undo, destructive decline/approve/undo, MIDI, local audio import/create/render/replace, unsupported-action honesty, cancellation, persistence, 10+ read/tool exchanges crossing 25k estimated context with no mismatched call IDs; verify usage, current/recent context retained, no secrets in log. Use a valid synthetic WAV and audio engine only if approved; keep existing music Set untouched. Verify installed package, not just developer CLI. If actual cache hit unsupported/unavailable, document evidence and acceptance decision rather than falsely passing. Provider account consent and real usage remain operator-gated.
6. **15.8 Close + delivery (orchestrator).** Reconcile branch/worktree and remote harness, review once, record exact revision/host evidence and unmet gates, then only under authorized delivery commit/push/open PR; wait for approval before main merge. Advance to Phase 16 only after required migration smoke and completed delivery criteria, or explicit owner decision on a genuinely blocked scope.

Expected effort: a moderate cross-cutting migration, not a one-file model change. Biggest unknowns: official sign-in eligibility, installed host system-browser/secure auth/network permissions, Responses schema compatibility and stream lifecycle. A simple provider spike should precede the rest. SDK/tool logic does not need a rewrite.
